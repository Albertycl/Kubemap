# Kubemap 0.2.0 release notes

Release 0.2.0 changes how Kubemap is deployed. The Windows service is gone. Kubemap is now a **web server that runs in the cluster** it shows, and you use it from the browser. There is nothing to register.

## What changed

- **One server in the cluster.** Deployment `kubemap` in `kubemap-system` serves the web UI on port 8080 over plain HTTP. Traefik ends TLS (cert-manager Certificate, IngressRoute on `websecure`; the defaults are host `kubemap.albertycliu.xyz` and ClusterIssuer `letsencrypt-prod`, `--host` and `--issuer` override them). SQLite lives on a 1 GiB volume.
- **The cluster agent runs inside the server.** It reads the Kubernetes API with the ServiceAccount `kubemap` (read-only, plus TokenReview).
- **No registration.** The cluster "this cluster" exists and is Active from the first start. There are no import commands, tokens, Accept, Reject, Rotate credential or Remove cluster, and the Add cluster pages are gone.
- **Node agents stay.** The DaemonSet `kubemap-node-agent` reports to the server through the cluster-internal Service. The server checks each agent's ServiceAccount token with a TokenReview. Several nodes work side by side; "node down" and "agent down" are told apart per node.
- **Removed:** the Windows `.exe` and service, the portal CA and certificate, `/v1/ca.crt`, `/v1/import.yaml`, `/v1/agent-bundle.yaml`, the separate cluster-agent Deployment and its credential Secret, the Windows scripts and `docs/install-windows.md`.
- **Install:** `deploy/install.sh` (or `kubectl apply -k deploy/`); see [install.md](install.md). One image from `deploy/Dockerfile` holds the server and the node agent (`make image`).
- **Renamed:** ClusterRoles `kubemap-readonly` and `kubemap-tokenreview`.
- **New:** default host `kubemap.albertycliu.xyz` and ClusterIssuer `letsencrypt-prod`; optional TOTP two-factor login (enrol under your user name in the top bar; `kubemap-portal disable-totp` recovers a lockout); `/healthz` no longer shows the version; "Internet exposure checklist" in [install.md](install.md).
- **Removed:** operator mode (the fix buttons, the `kubemap-operator` role and binding, the four guard policies, the `--operator` flags). Kubemap is **read-only by design** because the site is public. The ClusterRole holds only get, list and watch, plus TokenReview create. `deploy/uninstall.sh` still removes the old operator objects of an earlier install.
- **New: diagnosis hints.** A "What does this mean?" panel on the pod list and on pod and node findings: meaning, read-only kubectl checks with the real names filled in, likely causes and the source note title. Also for Service (no pods match the selector, or missing), Deployment and StatefulSet (fewer ready than wanted) and Pending PVC on the chain and app map pages. Text only; `GET /api/hints` is stateless and the catalogue is generated by `scripts/gen-hints.py`.
- **Login hardening.** An account-wide limit on wrong second-factor codes (10 per 15 minutes per user, then locked for 15 minutes, audit entry `totp_locked`), a higher limit (50) for failures that share one address, enabling TOTP ends the user's other sessions, and a missing `totp.key` is never re-created while TOTP is on.
- **Kept:** the audit log, the incident journal, admin login and `reset-admin-password` (now run with `kubectl exec`).

## How to upgrade from 0.1.x

There is no in-place upgrade: the old install is a Windows service plus agents that registered with it.

1. Stop the Windows service. If the old 0.1.x agents are still in the cluster, remove them with `deploy/uninstall.sh --yes`. Run it **before** the first install of 0.2.0 and never after: it deletes the namespaces `kubemap-system` and `kubemap-node`, including the volume (PVC) with the SQLite database. On a 0.2.0 install that means losing all its data.
2. Install 0.2.0 as in [install.md](install.md).
3. The database is new. Copy the incident journal over by exporting its entries as Markdown in the old version and using **Import Markdown** in the new one. The audit log starts empty.

## Known limits

- **Read-only by design.** Kubemap cannot change the cluster: no fix buttons, no operator mode. This is a choice, not a missing feature, because the site is public.
- The volume is ReadWriteOnce and the server has one replica, so it runs on **one node**. If that node is lost, the server is down until the volume is attached elsewhere.
- The node agents talk to the server over plain HTTP inside the cluster. The one-hour, audience-bound token, the TokenReview and the ingress NetworkPolicy limit the risk.
- The NetworkPolicy covers ingress only.
- One cluster per Kubemap. Showing several clusters needs a new design.
- The old registration tables stay in the database (unused), because migrations are checksummed.
- There is no registry yet; import the image into k3s on every node that runs a Kubemap pod.
